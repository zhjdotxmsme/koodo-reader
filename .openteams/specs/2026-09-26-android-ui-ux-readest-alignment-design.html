2. 现状（本会话核实的代码事实）

壳主题与导航

  • 极简app/.../shell/Theme.kt 全文 38 行，只有 4 个硬编码色值（primary #3A6EA5、secondary #6B8E23、浅底 #F8F6F2、深底 #16181D）；文件自带注释承认「真正的阅读器主题化是 P2 的事」。
  • 结构性问题LibraryScreen.kt 把 7 组互不相关的能力塞进一个 TopAppBar：4 个 IconButton（选文件 / 导入文件夹 / 备份 / 更多）+ 下拉菜单里的 视图切换、排序（多字段）、仅收藏、回收站、统计、词典、语言。
  • 路由现状ShellNavHost.kt：起始 library，另有 backup / trash / stats / dictionary 四个叶子路由，以及 reader/{bookKey}（按 format 分发 PDF / NativeEpub / placeholder）。无任何顶层导航容器。

技术底座（实测）

  • AGP 8.2.2 · Kotlin 1.9.24 · Compose 编译器 1.5.14 · navigation-compose:2.7.7 · compileSdk 34 / minSdk 24 / targetSdk 34。
  • Compose BOM 2024.06.00 → 解包 Gradle 缓存中的 material3-android-1.2.1.aar 实测确认：
  • 有surfaceContainer / surfaceContainerLow / surfaceContainerHighest / surfaceDim / surfaceBright —— 现代 M3 语义色角色齐全，不需要升级 BOM 就能用。
  • 有SegmentedButton · NavigationBar / NavigationBarItem · ModalBottomSheet · FilterChip · SearchBar · ListItem · PullToRefresh。
  • 没有NavigationSuiteScaffold 及 Material3 Expressive（需 BOM 1.3+）→ 平板/横屏自适应必须自建（见 R2）。

模块约定（决定了 D4）

  • :core:designsystem 是纯 Kotlin JVM 模块，自带零依赖注释、selfCheck 任务（gradle :core:designsystem:selfCheck）与无框架自检类。它承载 ThemeSpec / TypographyTokens / FontCatalogEntry / AppearanceCodec，字段与默认值是从桌面 styleUtil.ts / themeUtil.ts / themeList.tsx 逐条提取的协议镜像，用于保证 Room 与备份 zip 的线格式与桌面兼容。
  • 把 Compose 塞进这个模块会让 gradle test 从此需要 Android SDK，作废它应有的 JVM 门禁 —— 这正是选 D4 的原因。

⚠ 实测更正：:core:designsystem 是幽灵模块，其测试从未编译过

初版本 spec 把该模块的 selfCheck 当作"正在生效的既有门禁"，并以此作为 D4 的论据。用 Gradle 8.5 + JDK 17 实跑后推翻了这个前提，事实如下：

  • settings.gradle 的 29 个 include 中没有 :core:designsystem → 它不参与构建。
  • 全仓 build.gradle 无一依赖它 → 无消费者；全仓 Kotlin 代码 无一 import com.koodoreader.core.designsystem → 6 个源文件 + 5 个测试文件全是死代码。它只被别的模块在注释里当作"参考范式"提及，这正是它长期看起来活着的原因。
  • 用独立 settings 探针单独注册该模块后实跑：主源码 compileKotlin 通过，compileTestKotlin 失败，26 个错误：DesignSystemSelfCheck.kt 21×（failures 声明为 List<String> 却 add(it) 一个 Throwable）、ThemePresetTest.kt 3×（assertTrue 未导入）、FontCatalogEntryTest.kt 2×（assert(x, "msg") 签名误用；反引号测试名含 JVM 非法字符 :）。
  • 附带发现：FontCatalogEntryTest 有 3 处用 Kotlin 的 assert()，而它在 JVM 上默认不启用（需 -ea）且模块未开启断言 → 即使编译通过也是永不失败的真空测试，属仓库 scripts/check-phantom-tests.js 所防的那一类。

对设计的影响：D4 的决策不变（纯 JVM 可测性、不污染 Android 依赖、:core:ui 作为可复用设计系统，这些理由依然成立），但 W1 的范围与风险变了 —— 见 §9 与 R6。

笔记页的数据可行性（已核实，风险低于预期）

  • 已就绪core:data 的 Room 库 KoodoDatabase 已有 notes / bookmarks 两张表与对应 Entity/DAO。
  • 已就绪NoteDao.observeAll() 与 BookmarkDao.observeAll() 都已存在 → 跨书聚合零 DAO 改动、零 schema 迁移，只需 ViewModel 里 combine 两个 Flow 再 join books 取标题与封面。
  • 待验证engine/annotate 是决策层（三态模型 + CFI 编解码 + 列描述符），没有任何屏幕；从笔记列表跳进阅读器能否用 CFI 精确定位，见 R4。

并行改动面（影响第 2 步）

  • 热点文件android/settings.gradle 当前已被修改未提交，android/engine/fb2/ 未跟踪；.worktrees/ 下有十几个并行工作树。新模块注册必须单独提交、单独 review。

4. 分层与模块边界

:core:designsystem        （纯 JVM，本子项目不改其构建性质）
  ThemeSpec / TypographyTokens / FontCatalogEntry / AppearanceCodec
  ＋ 新增：KoodoColorTokens / KoodoShapeTokens / KoodoSpaceTokens（值对象，long 形）
        ▲  只当"值来源"，零 Compose 依赖，selfCheck 门禁继续有效
:core:ui                  （新增：com.android.library + Compose）
  theme/       KoodoTheme · KoodoColors · KoodoShapes · KoodoSpacing
               KoodoTypography · ThemeSpecBridge
  component/   KoodoScaffold · KoodoTopAppBar · KoodoSegmentedControl
               KoodoSettingRow · KoodoSectionHeader · KoodoEmptyState
               KoodoBookCover · KoodoBookCard · KoodoBookRow · KoodoChip
               KoodoBottomSheet · KoodoAlert · KoodoSlider
        ▲
:app/shell     ShellScaffold（底栏）+ 各页自有 TopAppBar
:feature:*     就地替换为 :core:ui 组件

三条硬边界

  1. :core:ui 不依赖 :core:data。 组件不认识 BookEntity，只吃 BookCardModel 这类 UI model。这条边界换来两件事：设计系统能被 :app 与 :feature:* 双向复用，且 Compose Preview 不需要数据库实例。
  2. ThemeSpecBridge 是唯一耦合点。 阅读页及其面板把 ThemeSpec 映射为 Compose ColorScheme；书库 / 笔记 / 统计 / 设置等外壳用品牌 ColorScheme，不受阅读主题影响。这是 D2「外壳对齐 readest、阅读页保留 koodo」在代码结构上的落点。
  3. :core:designsystem 保持零运行时依赖（纯 JVM）。 新增的只是纯 Kotlin 值对象 + 单测，不引入 Compose / Android 依赖。但注意：该模块当前未注册进构建且测试源码编译不过（见 §2 实测更正），所以 W1 的第一步是把它真正接上（注册 + 修 26 个测试编译错误），而不是"保持现状"。
为什么值对象与 Compose 绑定要拆两层。 androidx.compose.ui.graphics.Color 是 Compose 类型，若 token 本身用它，纯 JVM 单测就必须把 ui-graphics 拉上测试 classpath，对比度校验也就进不了 selfCheck。拆开后：色值在 :core:designsystem 是 long、间距是 Int/Float，可纯 JVM 校验浅深色槽位齐全与对比度 ≥ 4.5:1；:core:ui 只做 Color(0xFF…) 绑定。

为什么回收站与备份不放书库。 它们是数据管理能力，不属于"看书库"这一语境，且一年用不到几次 —— 放书库 TopBar 就是拿高频界面承载低频动作。readest 同样把 Sync & Backup 收在 Settings 下。它们仍是独立路由，只是入口挂在 设置 › 数据。

菜单拆解：按语境归属，不按功能

现在的位置去向理由
视图切换（网格/列表）、排序留在书库 TopBar 的「视图」菜单"我在看书库时的控件"，属于书库语境；readest 同样放在 library 的 View 菜单里
仅收藏留在书库「视图」菜单同上，是书库的筛选维度
回收站设置 › 数据跨页面数据管理，不是书库视图选项
备份 / 恢复设置 › 数据同上
统计升为顶层 Tab已有独立模块与屏幕，值得平级入口
词典设置 › 内容源配置型能力（导入/启用/排序），不是高频动作
语言设置 › 语言全局偏好
结果：书库 TopBar 从「4 个 IconButton + 7 组菜单项」收敛为「搜索 + 一个视图菜单 + 导入」。这是本次改动中用户可感知最强的一处。

两个明确的决定

  • 阅读器不进底栏（D11）。对齐 readest 的「控件随叫随到，不占用页面」：阅读是沉浸场景，常驻底栏会同时吃掉垂直空间和注意力。
  • 叶子页保留底栏（回收站、备份、词典管理）。它们是所属 Tab 的下钻，保留底栏让用户能横向切 Tab 而无需先返回 —— Android 标准行为。

6. 设计 token

6.1 颜色

品牌种子沿用现有 Theme.kt 的 4 个色值，按 M3 tonal palette 展开为完整 ColorScheme。观感规则对齐 readest 的扁平语言：

槽位取值 / 规则
primary#3A6EA5（沿用现有品牌蓝）
secondary#6B8E23 —— 降级为极少数 accent，避免与品牌蓝互抢
层级表达靠 tonal surface，不靠阴影：卡片 0dp elevation + surfaceContainerLow；浮层 surfaceContainerHigh
边界outlineVariant 1dp 发丝线做卡片与分隔 —— readest 平卡观感的核心，也是 koodo 现在最缺的一层
选中态统一走 secondaryContainer（底栏项、分段控件、筛选 chip），不用品牌蓝大面积铺底
浅色底#F8F6F2（沿用）
深色surfaceDim = #16181D 作页面底，surfaceContainer 系列逐级抬升

6.2 形状

KoodoShapes 覆盖 M3 默认的 medium / large：卡片与 BottomSheet 统一 16dp、控件 12dp、chip 8dp。readest 走 daisyUI 的 rounded-box(16) / rounded-btn(8)，这组是对位。

6.3 间距（M3 的结构性缺口）

ColorScheme / Typography / Shapes 这套 M3 三件套里没有 spacing token。补 KoodoSpacing：4 / 8 / 12 / 16 / 24 / 32。

这一层最容易被跳过，但跳过之后每个页面都会各自发明间距 —— 最终呈现就是现在这种「一个 TopAppBar 塞四件事」的堆叠感。它是本子项目里投入产出比最高的一项。

6.4 字体

UI chrome 用 KoodoTypography（基于 M3 + Inter / Roboto）。阅读页排版完全不动，仍走 :core:designsystem 的 TypographyTokens（与桌面一致）。这条边界保证本次改动不会波及 iframe/分页渲染这条敏感链路。

8. 验证策略

不能只靠"看着变了"。三层：

① 纯 JVM 单测（关键设计决定，见 §4）

  • 色值 / 间距 / 形状以纯 Kotlin 值对象形式放在 :core:designsystem，纳入既有 gradle :core:designsystem:selfCheck 门禁。
  • 校验项：浅色与深色的语义槽位齐全且一一对应；正文/背景对比度 ≥ 4.5:1；KoodoShapes 覆盖 M3 全部 5 档；间距标尺单调递增且无缺口。
  • 成果：设计系统的正确性进了 CI，而不是靠人眼。

② Compose Preview + 截图

  • 底栏（浅/深）、KoodoSettingRow、书库卡片与列表行各出 Preview。
  • 截图归档，供下一步与实施后对比。

③ 真机 / 模拟器冒烟

  • 4 个 Tab 均可达；叶子页返回栈正确；Tab 间切换不丢各自滚动/筛选状态。
  • 进出阅读器底栏不泄漏（D11 的回归点）。
  • 深浅色切换、横竖屏旋转不丢状态；minSdk 24 设备上无 API 越界崩溃。
  • i18n：语言切换后新页面文案全部跟随，无回退英文。
