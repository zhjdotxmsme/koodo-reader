0. 一句话结论

能逆向，且已拿到"官方壳如何处理引擎事件"的权威答案。 官方安卓端不是「WebView 套网页」的薄壳，而是 Expo SDK 54 / React Native 原生 UI + 自带 native 阅读引擎（react-native-kookit）+ 内嵌 lighttpd 本地 HTTP/WebDAV 服务 + WebView 内跑 kookit rendition 做渲染。 其对引擎事件的完整分派表为 33 个事件，与我们引擎的 22 个事件重合 17 个； 官方另有 16 个我们未处理的事件，我们另有 5 个官方未消费的事件。

4. 架构（逆向还原）

Expo/RN 原生 UI（阅读控制原生可证；书库 / 设置页为原生系推断，未证明） ← 由 index.android.bundle 驱动
  ├─ 经 react-native-kookit 模块直接访问引擎 API（反编译出现 ConfigService.getReaderConfig('cacheChapterCount') 等；经 JSI 还是 bundle JS 未定）
  └─ WebView 加载由 liblighttpd.so 提供的 本地 HTTP 页面（不是 file://）
      ├─ [jadx 已坐实] 服务链：getOpenPort 取空闲端口 → JS 构造 lighttpd config 写入磁盘（configPath）→ com.lighttpd.Server.start(id, configPath, errlogPath)（react-native-static-server 包装，System.loadLibrary("lighttpd")）→ WebView 加载 http://127.0.0.1:<port>/…
      ├─ [jadx 已坐实] document-root = app 私有目录（DocumentDirectoryPath + 子目录，配合 copyFile/writeFile/downloadAsync 在启动期把 kookit 引擎 JS 等写入）；具体子目录名为运行时变量，静态不可提取
      ├─ 注入 loadKookit()：动态插入 <script src='http://127.0.0.1:…/>' 加载 kookit → 回传 script-loaded
      ├─ 注入 ~42 处驱动脚本（调用点计），全部形如：
      │   window.rendition.<api>(...) → window.ReactNativeWebView.postMessage({event:...})
      └─ 引擎反向事件（select-text/left/right/swipe…）→ RN 侧 33 路 dispatcher
lighttpd 同时暴露 WebDAV 端点（书库可被其他设备挂载同步）
与我们的壳的根本差异：官方 = 原生 UI + WebView 只当渲染器（引擎 API 由注入脚本驱动）； 我们 = WebView 直接跑完整 web 应用（复用全部 UI 与功能，工程量小得多）。 两条路都能用；官方路线性能/手感更好，但需要重写 UI 层。

两点价值：
  • 本地 HTTP 而非 file://：WebView 拿到的是 http://127.0.0.1:port/…，Origin 是一个正常源 → 规避 file:// 下 localStorage/IndexedDB/ServiceWorker/CORS/跨文件访问的一堆限制（我们目前正踩这个坑）。

10. 对我们的行动建议（按性价比排序）

优先级项理由 / 依据成本
P0把壳从 file:// 换成本地 HTTP 服务 官方用 lighttpd；file:// 下 Origin 为 null，IndexedDB/localStorage/ServiceWorker/CORS 行为受限，长期是隐患。可用 NanoHTTPD / 自写 Kotlin ServerSocket / 复用 lighttpd 静态库中（半天级）
P0补 intent filters（VIEW/SEND） 官方覆盖 16 种电子书 MIME，文件管理器可「用 Koodo 打开」；我们的壳目前无此能力低（Manifest + onNewIntent 处理）
P1补 swipe-start / center / get-progress / chapter-text / pdf-js-ready / style-loaded / font-loaded 官方生命周期事件；注意这些可能来自其 Android 专用引擎构建，我们的 web 引擎未必会发——先验证再实现低（先加观察，再决定）
P1TTS 走近路：注入脚本用 visibleText/getRestAudioText 官方朗读是"原生 TTS + 引擎分段文本"；比在 web UI 里做更稳中
P1超大书内存：android:largeHeap="true" 官方专门写了 enableLargeHeap 插件极低
P2WebDAV 端点（mod_webdav 等价物） 把手机书库变网络盘；属于差异化功能，工程量大高
P2Release 打开 R8/minify + 自定义 proguard 规则 官方 release 开启 R8（我们 debug 不受影响，release 可减体积）中（需回归验证）
P2开源应用内更新 / 生物识别锁 官方有 REQUEST_INSTALL_PACKAGES + USE_BIOMETRIC（我们此前评估过生物识别）中

11. 边界与不可得

  • 授权边界：该壳不在 AGPL 仓库内（仓库只含 web/桌面端）。本报告用于互操作性参考；把其代码/资源直接搬进我们的分发包会有授权问题，应"照协议重实现"而非复制。
  • 不可得：native C++ 源码（阅读引擎核心）、原始 TS 工程结构、其签名私钥/OTA/IAP 凭据（本来也不在 APK 内）。
  • 整体复用不现实：官方壳强依赖闭源 native 模块、Expo 生态（expo-updates/IAP/Sentry/cloud-store）+ 一堆私有插件，搬迁成本高于自建。
  • 已部分解决（2026-09-17 复核，jadx dex 层）：web 页面机制已坐实——loopback lighttpd（com.lighttpd.Server，config 写磁盘）以 app 私有目录为 document-root，kookit 引擎 JS 启动期写入（copyFile/writeFile/downloadAsync 痕迹），WebView 加载 http://127.0.0.1:<port>/…。仍不可得：document-root 的具体子目录名（运行时闭包变量，静态不可提取；要拿精确路径需真机 logcat/抓文件系统）。
  • caveat：hermes-dec 反编译输出 7 条 pass4: LoadFromEnvironment references unknown register 警告 → 产物为 best-effort，个别函数有未解析寄存器；初版事件抽取曾用 40 万字符截断上限（分派器实长 690 万字符），复核已改跑全量，33 处理集合不变。
